# QuickRec Full v2.0 仓库贡献归属治理

## 文档状态

- 类型：v2.0 发布前技术治理门禁。
- 状态：已确认，待 v2.0 发布收口阶段实施。
- 产品影响：无业务功能变化。
- 当前执行边界：仅登记要求，不重写历史、不移动 tag、不修改 Release。

## 背景

QuickRec 早期 v1.1-v1.2 历史中有 14 个提交包含以下共同作者标记：

```text
Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>
```

GitHub 因此在仓库首页 Contributors 和 Insights Contributors 中显示
`claude`。该身份不是当前仓库 Collaborator，不拥有仓库读取、写入或管理权限，
也不影响 QuickRec 的运行与发布；问题仅属于历史贡献归属和仓库展示治理。

## v2.0 必须完成的目标

v2.0 正式发布前必须完成以下事项：

1. GitHub 仓库首页 Contributors 不再显示 `claude`。
2. GitHub Insights Contributors 不再把上述 14 个提交归属给 `claude`。
3. 后续提交不得再包含 Anthropic/Claude 的共同作者标记。
4. v1.1-v1.9.2 及后续已发布 tag 的对象与 peeled commit 不得被移动或覆盖。
5. 历史 GitHub Release、发布说明和二进制资产必须继续可访问。
6. Full 与 Lite 的当前分支、配置、CI、发布身份不得因治理发生混线。
7. 治理完成后必须提供新的 clone、pull 和回滚说明。

## 强制前置审计

执行任何历史或默认分支治理前，必须：

1. 导出包含全部 refs 的 Git bundle，并在独立目录验证可恢复。
2. 建立只读 mirror clone，记录所有本地与远端分支 SHA。
3. 记录全部 annotated/lightweight tag 对象及其 peeled commit。
4. 记录全部 GitHub Release、资产名称、大小和 SHA256。
5. 记录 Full、Lite 当前分支、默认分支、保护规则和 CI 触发条件。
6. 检查 fork、开放 Pull Request、外部 clone 和自动化部署的影响。
7. 输出执行方案、回滚方案和预计维护窗口，等待用户再次明确授权。

## 方案门禁

v2.0 实施阶段必须先比较并验证：

1. GitHub 平台是否提供不重写历史的归属修正方式。
2. 保留全部历史 tag、以 v2.0 建立新的默认分支基线是否可行。
3. 重写默认分支提交信息的影响范围及是否会破坏发布追溯。

不得把 `.mailmap` 当成已验证方案；它主要映射 Git 作者和提交者身份，
不能在未经 GitHub 实测的情况下假定会移除提交正文中的共同作者归属。

## 禁止事项

在未完成前置审计和二次授权前，禁止：

- force push `master`、`test`、`lite-master` 或 `lite-test`；
- 删除、移动或覆盖任何历史 tag；
- 删除历史 Release 或重新上传覆盖发布资产；
- 修改 14 个历史提交后直接推送；
- 通过删除仓库并重建同名仓库规避历史治理；
- 把该治理混入 v1.9.3、v1.9.4 的业务功能提交。

## 验收证据

v2.0 发布前至少保留：

- 治理前后的 Contributors 页面截图；
- 治理前后的全部分支和 tag SHA 清单；
- Git bundle 和 mirror clone 恢复验证记录；
- 历史 Release 与资产可访问性抽样结果；
- Full/Lite CI、打包和回滚验证结果；
- GitHub Contributor 数据刷新后的最终确认。

## 发布判断

只要 GitHub 仍将 `claude` 显示为 QuickRec Contributor，或历史 tag、Release、
分支恢复能力存在不一致，v2.0 就不得进入最终发布。
